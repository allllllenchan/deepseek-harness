# Agent Note: job_output waits on output conditions and bounds its own reads

Status: implemented

[English](2026-09-23-job-output-output-conditions.md) | 中文

## 问题

`job_output(wait: true)` 只可能在任务结算或到达时限时结束。因此，对于会打印出模型正在等待的那一行、随后继续运行的任务，并不存在「那一行到达即结束」的等待。观察到的绕行做法是循环执行 `Start-Sleep -Seconds 420` 再重新读取一次：每轮都要花一个模型步，把它花在调用方并未要求的日志印记上；而且由于每次读取都会消费自己的增量，还会吞下调用方再也拿不回的片段。工具自己的提示词让模型不要轮询、不要 sleep，却没有给出更好的选择。

同一次读取也没有调用方侧的限额。`tail_lines` 与 `max_bytes` 并不存在，因此「给我看那一段的结尾」只能通过取回整段、再由后续截断来决定来表达。

三个已发布的后台生产方中，有两个注册任务时没有 `outputLimitBytes`：`tool-terminal` 声明了 `maxResultBytes`，而 `tool-bash` 与 `tool-pwsh` 什么都没声明。执行器的内存输出窗口限定的是进程保留多少，而不是面向模型的读取或完成通知可以返回多少：有损读取会返回整个保留窗口，部署可以调高该窗口，而携带模型所写命令的完成通知在生产者层完全没有界。

## 决策

`job_output` 接受三个可选参数。`pattern`（配合 `wait: true`）在某次读取的输出包含该字面文本时结束等待，调用返回截至该处的已读输出（含命中文本）。`tail_lines` 只返回末尾 N 行。`max_bytes` 限定完整的面向模型结果。

### 等待仍是任务唯一的输出消费方

pattern 等待采用增量读取：读取自上次读取以来的增量，追加进一个有界的 `TextRetainer`，用「迄今读到的输出」检测该 pattern（并携带上次读取的最后 `pattern.length - 1` 个字符，因此跨越两次读取断开的匹配仍能被发现），否则经 `ctx.jobs.wait` 等待一个 `patternPollIntervalMs` 节拍。它在命中、终止状态、截止时间或调用方取消时结束；四种结局都返回迄今读到的输出与任务实时快照，且都不是错误。

这保持了能力 seam 的单游标规则：等待循环仍然是一次 `job_output` 调用在读取任务，与等待后单次读取完全一致。改变的只是这个消费方读一次还是反复读。对同一个流式任务并发发起两次 `job_output` 仍会争抢增量，而这种情况此前就已存在。

调用方的输出会被交付而不是丢弃。等待读到的所有内容都会被保留并返回，因此通往命中途中消费掉的输出会送达模型；另一种做法会消费掉只有该等待在读取的字节，使之不可恢复。仍可能丢弃内容的只有显式声明的限额，而每个此类限额都会在返回文本开头说明自己的省略：`tail_lines` 用 `[earlier output omitted: N lines]`，调用方与生产方都未声明字节预算时等待所施加的保留上限用 `[earlier output omitted: N bytes]`。

### 一个字节界，由调用方收紧

`max_bytes` 解析进既有的生产方界，而不是引入第二套截断：前置的 `tools/pre-execute` 监听器本就读取调用方可见任务的 `outputLimitBytes`，现在它对 `job_output` 返回 `min(producerLimit, max_bytes)`。随后 `finalizeContent` 经由既有机制限定完整渲染结果——该机制已经为 `[status: ...]` 后缀预留空间并复用已有的截断标记——因此错误、策略替换与流水线失败都以同样方式设界。结果值保持其 `{ text, job }` 约定。

不带 `wait: true` 的 `pattern` 会被拒绝，而不是静默失效；非字符串或空 pattern，以及非正的限额，同样被拒绝。

### 轮询节奏与保留量是配置项，而非隐含假设

`patternPollIntervalMs`（默认 250 毫秒）是一个 `Config` 字段：它在检测延迟与读取频率之间取舍，而不同部署的取舍不同。等待没有字节预算可花时的保留上限是固定的 `MAX_WAIT_RETENTION_BYTES`（1 MiB）——这是内存安全界，不是策略旋钮，因为调用方已经通过 `max_bytes` 掌握该维度；它会报告自己丢弃了多少。

`tool-bash` 与 `tool-pwsh` 新增 `maxResultBytes`（默认 256 KiB，对应 `tool-terminal` 的 `DEFAULT_MAX_RESULT_BYTES`），并把它作为任务的 `outputLimitBytes` 传入。该默认值刻意高于执行器默认的每流 64 KiB 窗口，使一次正常的 stdout 加 stderr 有损读取不会被截断两次；这个上限是为调高的窗口、为完成通知，以及为与第三个生产方对齐而存在。

## Alternatives considered

- **在生产方约定上增加非消费式输出预览。** `JobHooks.previewOutput()` 能让等待在不消费的情况下检测输出，但为避免一个消费方自己就能拥有的保留缓冲区，它会改变每个生产方都要实现、每种任务 kind 都要继承的约定。
- **在 `tool-jobs` 内按任务维护一张未命中增量表。** 它无需保留器即可满足「后续 `job_output` 仍能读到」，但把游标状态移出了任务，没有自然生命周期（所有者释放、teardown、id 复用），而且对恰恰不要求任何界的调用方完全没有界。
- **只返回命中的那一段。** 对动机场景最省，也丢得最多：等待是唯一的读取方，因此该段其余内容就此消失，而想要周边上下文的调用方无从索取。
- **用正则作为 `pattern`。** 字面子串让面向模型的约定不涉及方言问题、不产生调用方必须处理的非法 pattern 失败，也不暴露灾难性回溯。
- **在 `ctx.jobs` 上增加输出进度事件。** 那会要求所有生产方都发布字节进度，而注册表的变更流描述的是可见任务集合而非字节；轮询单个任务的游标完全由本消费方自己拥有。
- **让 `pattern` 隐含 `wait: true`，或在没有 `wait` 时忽略它。** 隐式阻塞会隐藏一个调度决定，静默失效的参数会隐藏调用方的错误；拒绝会点明修法。
- **在 `ctx.jobs.wait` 内部限定等待的保留量。** 界属于「完整结果已知」的位置，也就是渲染该结果的工具；注册表没有可供设界的面向模型结果。

## Consequences

本来会 sleep 七分钟的模型，现在阻塞在它需要的那一行上，并收到通往该行的输出。被阻塞的等待不再需要靠猜一个 `timeout_ms` 才有用，而拿到答案的调用方仍可对一个正在运行的任务采取行动。

代价是：pattern 等待在等待期间每个轮询节拍都会读取一次，因此一个不产生任何输出的任务每节拍消耗一次读取与一个 `ctx.jobs.wait` 等待方；匹配最多在该字节到达后一个节拍才被察觉（已记为本包的一条限制，因为注册表没有可供订阅的输出通知）；等待在运行期间最多在内存中持有调用方的字节预算——没有预算时是 1 MiB。

验证：`packages/jobs/tool-jobs/tests/tool-jobs.spec.ts` 固定了提前返回、跨两次读取断开的匹配、面向存活任务的超时、无命中的结算、命中前所读增量的无损交付（含游标已越过它们这一点）、`tail_lines` 及其省略标记、`max_bytes` 只能收紧而永不放宽生产方上限、三个参数的组合、保留上限、每一个被拒绝的参数，以及加载期的节奏守卫。`packages/shell/tool-pwsh/tests/tools.spec.ts` 固定了所声明的生产方上限、它对一次读取的截断效果，以及裸配置守卫；`packages/shell/tool-bash/tests/tools.spec.ts` 经由其真实任务运行时固定同样的上限与守卫。
